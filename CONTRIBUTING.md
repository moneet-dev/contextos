# Contributing to ContextOS

Thanks for your interest. ContextOS is early, and help is welcome: code, test
incidents, evaluation runs, or reports of where the context was wrong.

## Where to start

- Issues labelled
  [`good first issue`](https://github.com/moneet-dev/contextos/labels/good%20first%20issue)
  are small and self-contained.
- Issues labelled
  [`help wanted`](https://github.com/moneet-dev/contextos/labels/help%20wanted)
  are larger pieces of the [roadmap](ROADMAP.md).
- For anything bigger than a bug fix, open an issue or comment on one first, so
  we can agree on the approach before you write the code.

## Setup

Requires Java 17. Python 3 is needed only to regenerate the fixtures.

```bash
./gradlew test                  # all modules
./gradlew :contextos:demo       # cross-domain investigation of INC-143
```

The fixtures in `examples/runtime` are generated by
`python examples/runtime/generate_fixtures.py`. Edit the generator, not the
generated files, and commit both.

## Guidelines

- **Each domain stands alone.** `schema-context` (the Schema Context Engine)
  must not depend on any ContextOS module. Changes to its public API should be
  additive. The code and incident modules depend only on `contextos-core`.
- **Ranking stays explainable.** Scores are products of named factors that are
  shown next to each item. No opaque scoring and no LLM in the context pipeline.
- **Every item carries provenance:** where it came from and why it was chosen.
- **Tests come with the change.** New behaviour needs a test; new fixtures or
  incidents need a test that pins their counts or ranking.
- **Evaluation inputs are versioned.** If you change `examples/eval/cases.json`,
  add an entry to its `revisions` list explaining why. Results graded against
  different rubrics are not comparable.
- **No secrets in the repository.** API keys go in a local `.env` (ignored by
  git); database passwords are read from environment variables named in
  `contextos.json`.
- Match the style of the surrounding code. Keep pull requests focused, and
  describe what changed and how you tested it.

## Reporting problems

Open an issue with what you ran, what you expected and what happened. If the
context for an incident ranked the wrong evidence first, include the incident
and the rendered package: those reports are among the most useful.
